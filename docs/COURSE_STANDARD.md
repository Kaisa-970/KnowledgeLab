# 课程设计与内容标准（v0.1）

本规范供课程设计 Agent、课程编辑器、交互组件开发者及审稿 Agent 共用。与 `AGENTS.md` 同时生效。

**认知设计前置：** `docs/LEARNING_EXPERIENCE_CONTRACT.md` 规定如何针对当前学习者建立理解；本文件与 Course Contract v2 负责知识正确性与可验证交付。

## 0. 知识树归属先于课程计划

新主题先按 `docs/CURRICULUM_CONTRACT.md` 定位全局主线、模块与已有/规划课程，优先改进已有章节；仅独立持续性主题才考虑新 Course。归属必须在 manifest 中唯一登记并通过机器校验，但语义上是否必要新课仍由维护者审查。

## A. 课程级交付物

每门课建议产生（新课程或重大改稿时）：
- `course.plan.json`：`id`、`title`、`domain`、`level`、`summary`、`prerequisites`、`learningOutcomes`、`chapters` 等；
- 章节依赖图：先修概念、当前章节与后续知识节点；
- 每章一份 MDX，独立交互组件放 `src/components`；
- 关键实验说明（模板见下）与测试；
- 来源、复审与版本记录。技术时效性高的材料需要注明日期。局部改动只需记录受影响范围和复用的设计依据。

课程学习目标用可观察行为表达（例如“能够解释为何特征向量反映不改变方向的向量”），不要用空泛的“了解”“熟悉”。

## B. 课程叙事与知识体系（最高优先级）

课程不应模仿“定义 → 定理 → 例题”的教材组织，也不应该变成“开场问题 → 动画 → 公式 → 应用”的新模板。**问题驱动的是读者的认知路线，不是固定目录。** 新课程、改变课程主线的重大改稿，或新增跨章节知识连接时，以 `docs/LEARNING_DESIGN.md` 为详细依据，在开写正文前准备 `docs/templates/learning-brief.md`（内部审阅即可，课程正文不直接照抄标题）。局部修正、测试修复和视觉/实现调整不要求重新提交完整 Brief。

必须清楚回答四个问题：

1. **为什么（Motivation）**：读者面对什么具体困惑或现有办法的限制，值得为它寻找新工具？
2. **如何（Understanding）**：直觉如何建立，因果机制如何工作，形式化的定义/证明又为什么成立？
3. **哪里（Connection）**：在当前学科/知识网络中的位置是什么，具体依赖哪些先修知识、和什么概念容易混淆、用到哪里？
4. **然后（Transfer）**：新知识帮助解决什么，读者能否把它迁移到未演示的新问题？

**课程级设计**：
- 使用 `course.plan.json` 规划真实先修关系，不能把所有知识联系塞进 `dependsOn`。
- 在 `knowledge-map.json` 记录“共同原理、推广、区别、应用”的端点、类型、理由与边界，正文解释其教学意义。
- 章节之间应由未解决的问题自然衔接，避免每节像独立词条。
- 严格理论、关键计算、反例、适用条件和练习**仍然必需**，但应在读者有需求时出现。
- 可以用一张静态图解释核心问题，也可以完全用文字或数学证明；不强制每节有 SVG 动画或交互。
- 避免为了讲故事而编造历史/科学家动机。需要历史背景时标来源。

**改写既有课程**：保留正确数学结果和组件，首先重写“为什么从这个问题开始”“每个新公式此时解决什么”“最后如何回扣与迁移”，然后再根据认知障碍决定是否要加图。

## C. 交互实验契约

每个核心实验在制作前应具备下列设计信息（可记录在任务/PR 或未来的结构化文件中）：

```yaml
id: matrix-basis-lab
question: "为什么矩阵可以看作基向量被映射到的位置？"
prediction: "只改变第一列时，哪个基向量会改变？网格会怎样？"
controls:
  - "拖动变换后 e₁、e₂ 的端点"
  - "修改 a, b, c, d"
visible_outputs:
  - "变换后的网格和两个基向量"
  - "矩阵、行列式、输入向量的结果"
invariants:
  - "T(0)=0"
  - "T(e₁)=矩阵第一列，T(e₂)=第二列"
edge_cases:
  - "det(A)=0 时面积塌缩"
  - "det(A)<0 时朝向反转（手性改变），注意不等于每个向量都掉头"
test_oracle:
  - "T(2e₁+3e₂)=2T(e₁)+3T(e₂)"
  - "det(A) 与有向面积缩放因子一致"
explanation: "列向量决定基向量去向，线性性决定其余点去向"
```

本节 `C` 仅适用于实际需要交互的课程。若章节不适合交互，使用受 Schema 约束的 `coreTask`（`labIds` 与 `coreTask` 二选一）；只有新课程、重大改稿或该章节改变主线时，才需要在 Learning Brief 说明媒介选择理由。实验不能为了填满 Schema 而写空洞控件。

所有交互控件都需要具备：输入范围/约束、默认状态、重置或预设、文字反馈、坐标和单位约定、至少一个对照状态。更改数据时应通过同一计算模块更新公式与画面。

## D. 主路径与渐进深入

- **Understand — 短主路径**：聚焦一个主要理解障碍，用一个正确、可预测的例子建立因果模型；读者可在这里停下。
- **Derive / Implement — 深入路径**：可选地展开完整数学推导、运行机制或关键实现。核心公式恰好说明当前问题时应直接出场，不机械折叠。
- **Transfer / Boundary — 迁移与边界**：解释新情境、适用条件与反例；必要纠错边界不能藏到读者看不到的地方。

这是掌握深度的区分，不是固定三段式页面或固定 5/15/30 分钟；应跳过目标读者已掌握的基础知识。

## E. 数学、代码与可视化细则

- 提供术语英文对应，但正文以中文自然表达。
- 公式在 MDX 中用 `$...$` 或 `$$...$$` 书写；包含下标、矩阵时实测 KaTeX 渲染，不用截图替代文字公式。
- 矩阵采用明确的行/列约定；坐标系明确左/右手性及轴向；张量标注 shape；概率变量明确随机含义。
- 实验使用可确定的种子或固定例子，给出合法输入范围；极值和退化输入需要解释。
- 避免无依据的“显然”“容易得出”，至少给出关键因果理由。
- 对运行开销、数值精度、训练/推理与仿真/真实部署的区别，避免过度简化。
- 交互无法正确表达的内容宁可使用严谨静态图加推导，也不要生成误导动画。

## F. 课程验收清单（独立内容审查，非 CI 可代替）

- [ ] **叙事盲测**：暂时不看公式与动画，仅阅读主要段落，能否说清“为什么学 → 困惑在哪里 → 突破口 → 解决了什么”？
- [ ] **已有认知与压力风险**：确认已知与猜测是否分开？基础是否重复？陌生术语与新数学对象是否无必要地集中引入？
- [ ] **最小理解闭环**：读者能预测一个结果、识别旧模型不足并解释未直接示范的变式吗？
- [ ] **主路径与退出点**：只读主线能否形成正确而有限的直觉？完整理论仍可按需深入吗？
- [ ] 新概念的出现是否由已有问题自然引出？不是开场问一句然后直接堆定义？
- [ ] 已有知识能解释到哪一步、新方法在哪一步更有用，是否明确？
- [ ] 数学/代码的关键细节、条件、维度和边界是否独立正确？
- [ ] 知识节点的上游先修、同层对比/共同原理、下游迁移是否有**解释**，而不是只有标签？
- [ ] 至少有一个真正需要迁移推理的练习，以及可检查的参考解释？
- [ ] 如有图片，它是否回答具体问题，并满足 `docs/VISUAL_ASSETS.md` 的事实/许可证/图注/alt 要求？
- [ ] 如有交互，它是否改变学习者的预测或理解，且数值、画面与数学测试一致？
- [ ] 如不用交互，`coreTask` 是否具有真实的可验证目标而非空洞占位？
- [ ] Schema、数学数值检查、TypeScript、构建、浏览器测试实际运行的结果与未完成项是否单独列出？
- [ ] 是否既能自然讲清楚来龙去脉，又有足够严谨的理论深度？

阅读 `.claude/skills/course-review/SKILL.md` 进行审核；**结构校验通过不等于教学质量通过**。

## G. 机器可读内容契约

课程元数据的唯一来源是 `course.plan.json`（不是同时维护 `course.json` 与另一份课程计划）。必须通过 `schemas/course-plan.schema.json`。每个 `labIds` 指向 `src/content/labs/<id>.lab.json`，其 `invariants` 与 `edgeCases` 的 `oracleIds` 必须指向已有 `oracles`，各 `testFile` 和 `testName` 必须指向真实测试。规范和可执行校验见 `docs/CONTENT_CONTRACTS.md`。

Schema 能检验字段存在、引用完整和依赖无环，无法从自然语言证明数学正确性；它不替代推导审核和真实交互检验。生成代码不得直接越过 PR 审核进入正式部署。
